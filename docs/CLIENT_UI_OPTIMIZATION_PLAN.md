# EncoreHub 客户端页面优化计划

> 状态：修订提案 v2
> 基线日期：2026-07-24
> 目标参考：用户提供的布局、消息状态、Token 与供应商设置参考图
> 范围：客户端主窗口、角色/对话侧栏、聊天上下文栏、消息流、输入区和供应商配置页

## 一、修订结论

本方案严格按参考图的页面骨架设计，不再采用上一版的“活动栏 + 多工作区”布局。

目标结构只有五个稳定区域：

1. 顶部全局导航栏。
2. 左侧“角色 / 对话”双模式侧栏。
3. 主区顶部“角色 / Provider / Model”上下文栏。
4. 中央文档式对话区。
5. 底部一体式输入区。

知识库、记忆、Skills 等能力继续通过设置、工具菜单或后续功能入口访问，本轮不把它们做成左侧一级导航。

### 与上一版方案的差异

- 删除 48px 活动栏和模块级上下文侧栏。
- 左侧固定为“角色 / 对话”切换，不按 Knowledge、Memory、Skills 切换。
- 主区消息宽度从约 768px 调整为适合参考图的 960–1080px 文档流。
- 用户消息使用右侧紧凑气泡；模型回复保持左侧文档流，不做对称双气泡。
- 模型回复明确拆成“思考过程”“最终回复”“本轮操作”三层。
- Provider/Model 从侧栏底部移到主区顶部上下文栏，完整配置页采用纵向表单。
- 输入框改为参考图中的大尺寸双层输入工作台，固定在主区底部。
- 为匹配顶部布局，自定义桌面标题栏进入目标范围，但分平台逐步启用。

## 二、目标布局

```text
┌──────────────────────── 顶部全局导航栏 64px ─────────────────────────┐
│ [首页] [角色] [+]                      [外观] [设置] [－][□][×]     │
├──────────── 左侧栏 300px ───────────┬──────── 主工作区 ─────────────┤
│  [角色]              [对话]         │ [收起] 角色 > Provider·Model     │
│  ─── active underline ───          │                    [选项][专注][搜索]│
│                                     ├───────────────────────────────┤
│  + 添加角色 / + 新建对话             │                               │
│                                     │        文档式消息流             │
│  [头像] 默认角色              [⋮]   │        max 1080px              │
│  [头像] 编程角色              [⋮]   │                               │
│                                     │                               │
│                                     ├───────────────────────────────┤
│                                     │  输入消息…                     │
│                                     │  [命令][搜索]     [状态][发送]  │
└─────────────────────────────────────┴───────────────────────────────┘
```

### 尺寸基线

| 区域 | 桌面尺寸 | 约束 |
|---|---:|---|
| 顶部全局导航 | 64px 高 | 固定，不随内容滚动 |
| 左侧栏 | 默认 300px 宽 | 最小 260px，最大 380px，可拖拽 |
| 主工作区外边距 | 8–12px | 与参考图一致，主区形成独立白色工作面 |
| 主区顶部栏 | 64px 高 | 固定在消息区上方 |
| 对话正文 | 最大 1080px | 水平居中，左右至少保留 32px |
| 输入区 | 默认 136px 高 | 最小 104px，textarea 最大展开至 220px |
| 常规图标按钮 | 32×32px | 图标 16px，尺寸不因状态改变 |

主工作区是页面主体，不使用卡片嵌套。其白色工作面可以有 10–12px 外轮廓圆角；内部消息、顶部栏和输入区通过留白与细分隔线组织。

## 三、区域设计

### 3.1 顶部全局导航栏

目标：复现参考图的应用级导航和窗口控制，避免再额外叠一层浏览器式工具栏。

#### 左侧

- **首页**：进入聊天主页，选中态为白色浅底块，包含 Home 图标与文字。
- **角色**：进入角色管理页；在角色数据模型完成前不显示不可用死入口。
- **加号**：在首页创建新对话；在角色页创建新角色。两类能力都存在后可改为短菜单。

#### 右侧

- **外观**：使用显示器/主题图标打开 light、dark、system 菜单。
- **设置**：打开现有 Settings。
- **窗口控制**：最小化、最大化/还原、关闭。

#### Tauri 实现规则

- Windows 目标形态使用自定义标题栏，导航与窗口按钮处于同一 64px 区域。
- 使用 `data-tauri-drag-region` 标记顶部空白区域；所有按钮从拖拽区域排除。
- 支持双击空白区域最大化/还原、窗口拖动、最小化、最大化和关闭。
- 自定义控制全部通过实机验收后，才把 Windows `decorations` 设为 `false`，避免出现不可拖动窗口。
- macOS/Linux 在完成平台专项验收前保留原生装饰；不能为了 Windows 视觉效果破坏其他平台窗口行为。
- Web 开发模式保留同一导航结构，但隐藏系统窗口按钮。

### 3.2 左侧“角色 / 对话”侧栏

目标：与参考图一致，在同一个侧栏位置切换“选择什么角色回答”和“选择哪段对话”。

#### 顶部标签

- 两个等宽标签：`角色`、`对话`。
- 选中态使用 2–3px accent 下划线和主文字色，非选中态不加背景卡片。
- 侧栏记住上一次标签选择；新安装默认进入 `对话`，优先保证历史对话可见。
- 切换标签只替换侧栏内容，主聊天区不卸载、不丢失输入草稿和滚动位置。

#### 角色标签

- 第一行是“添加角色”命令，使用 Plus 图标与文字。
- 角色列表项显示头像、名称和更多菜单；选中项使用白色底、细边框和极轻阴影。
- 单击角色后，主区顶部同步显示该角色，并打开其最近对话或空白新对话。
- 更多菜单包含重命名、复制配置、删除；默认角色不可删除。
- 当前项目尚无独立角色配置实体。第一阶段仅提供由当前 Provider/Model 投影出的“默认角色”，不显示不可用的“添加角色”。
- “角色”是一等领域实体，不只是 Provider/Model 的显示别名。用户可以为角色定义角色级全局提示词，并在以后创建的多个对话中复用。
- 界面术语使用“角色”，但代码中不建议直接新增 `Role` 类型，因为 `Message.role` 已表示 user/assistant/system/tool。为兼容角色卡语义，建议使用 `CharacterProfile` 与 `character_id`。
- 最小角色字段包含：名称、头像、角色描述、全局提示词、默认 provider/model、开场白、标签、版本号和更新时间；skill/knowledge 绑定作为可选扩展。
- 创建对话时同时保存 `character_id`、角色版本和提示词快照。角色后续修改默认只影响新对话；旧对话通过显式“升级角色版本”操作更新，避免历史行为静默漂移。
- 角色编辑页提供大尺寸“全局提示词”编辑器、变量说明和 token 估算；保存、测试对话与导入角色卡是明确命令，不在输入框周围堆叠说明文字。

#### 酒馆角色卡兼容预留

- 内部 `CharacterProfile` 使用版本化 schema，导入/导出通过适配器完成，不让页面组件直接解析角色卡 JSON 或 PNG metadata。
- 首个兼容阶段覆盖常见 Tavern/SillyTavern 角色卡字段：名称、头像、description、personality、scenario、first message、example dialogue、system prompt、post-history instructions、alternate greetings、tags 与扩展数据。
- 对未知字段和 `extensions` 做原样保留，保证“导入后再导出”不会无故丢失第三方扩展。
- JSON 卡与 PNG 内嵌 metadata 使用同一规范化管线；解析器放在 Engine 或独立领域模块，设置文件大小、图片尺寸和文本长度上限。
- 导入前显示字段预览与冲突处理，默认创建新角色，不自动覆盖同名角色。
- 角色卡中的提示词视为用户提供内容，不能获得高于应用内部安全/工具边界的权限，也不能执行其中的脚本或远程资源。
- 酒馆角色卡具体版本与字段映射应形成单独兼容契约和样例夹具；本轮 UI 只确保数据结构与页面布局不会阻塞后续适配。

#### 对话标签

- 第一行是“新建对话”命令；其下可增加本地标题搜索。
- 对话直接对应现有 `Conversation`，按 `updated_at` 分为今天、昨天、过去 7 天、更早。
- 列表项显示标题；次要信息按空间显示更新时间或模型简称，不同时堆叠过多元数据。
- 当前对话使用白色底和 2px accent 左边线；hover/focus 显示更多菜单。
- 更多菜单提供重命名、重新生成标题和删除；不再把删除图标永久悬浮在列表尾部。
- 双击重命名可以保留，但不能作为唯一可发现入口。

#### 侧栏行为

- 列表独立滚动，顶部标签和新增命令保持可见。
- 保留当前拖拽调宽与本地持久化能力，将范围收敛到 260–380px。
- 侧栏折叠后完全隐藏，由主区顶部栏的 PanelLeft 按钮恢复；不保留额外的 48px 图标栏。

### 3.3 主区顶部“角色 / 模型”栏

目标：在参考图“场景/模型”位置明确显示当前角色、Provider 和 Model，让用户在发送前确认回答上下文。

#### 左侧顺序

1. 收起/展开侧栏按钮。
2. 角色头像与名称。
3. 角色切换箭头。
4. Provider 标识。
5. Model 名称与下拉箭头。

#### 右侧命令

- 会话参数：只有温度、推理强度等设置真正接入发送请求后才显示。
- 专注模式：隐藏侧栏并扩大消息区域，可以立即实现。
- 对话内搜索：需要先实现当前消息本地搜索；未实现前不显示放大镜假按钮。
- 更多菜单：重新生成标题、删除对话等低频命令。

#### 数据语义

- 新对话尚未创建时，Provider/Model 控件修改“新对话默认值”。
- 已创建对话必须展示其 `Conversation.provider/model`，不能直接展示 `settingsStore` 全局值。
- 当前后端只支持修改对话标题，Provider/Model 在创建后实际上是权威元数据。
- 如果用户在已有对话中选择其他模型，应明确执行“使用该模型新建对话”，不能让界面显示已切换而请求仍使用旧模型。
- 角色实体落地后，新对话继承角色默认模型与全局提示词快照；对话自身仍保留最终 provider/model、`character_id` 和角色版本，保证历史可审计。
- Gateway 组合 system prompt 时采用固定顺序：应用基础约束 → 角色全局提示词/角色卡内容 → Skill 指令 → Memory/Knowledge 上下文 → 工具说明。各段使用明确边界，不做不可审计的字符串混写。

### 3.4 中央对话区

目标：按第二张参考图组织每一轮消息，形成“用户指令 → 思考过程 → 最终回复 → 本轮操作”的清晰阅读顺序。

```text
                                           ┌ 用户消息气泡 ┐
                                           │ 提交当前未提交… │
                                           └──────────────┘

已处理 1m 51s  [展开/收起]
思考过程正文……

最终回复正文……
- 结果一
- 结果二

[复制] [重新生成]                [131.26 tok/s] [160 tokens] [0.40s] [EOS]
```

#### 用户消息

- 用户消息右对齐，使用中性浅灰紧凑气泡；不使用大面积 accent 实色。
- 气泡最大宽度为对话正文的 72%，短消息按内容收缩，长消息自然换行。
- 圆角 12px 左右，正文 14–15px；不显示重复的“用户”头像和标题，减少噪声。
- hover/focus 时可显示复制与“编辑并重发”；编辑并重发必须创建新 turn，不能直接改写已持久化历史。

#### 思考过程

- 模型回复包含 `reasoning` 时，在最终回复上方显示独立的可折叠思考区。
- 标题行使用 `思考中 12s`、`已处理 1m 51s`、`已停止` 或 `处理失败`，右侧放展开/收起 Chevron。
- 流式思考默认展开，并随 reasoning 增量更新；最终回复开始后保留用户当前展开状态。
- 历史消息首次载入时默认折叠，避免长对话被大量思考文本撑开；用户手动展开后在当前会话内记忆状态。
- 思考正文使用次要文字色和略紧凑行高，不放入重边框卡片；可用顶部细分隔或左侧弱色引导线区分。
- 当前前端可以记录本次流式耗时，但 `Message` 尚未持久化 duration。第一阶段历史消息只显示“已处理”；若要在刷新后保留 `1m 51s`，需为消息契约增加 `duration_ms`。
- reasoning 内容沿用现有安全策略，不额外制造或推断模型未返回的思考文本。

#### 最终回复

- 最终回复位于思考区之后，左对齐并采用无卡片的 Markdown 文档排版。
- 不重复显示大头像；可在整轮顶部用小型模型标识，或仅由主区上下文栏表达当前模型。
- 标题、段落、列表、表格、引用和代码块维持明确层级；纯文本行宽建议控制在 70–85 个字符，表格和代码可使用完整内容宽度。
- 工具调用插在思考区与最终回复之间，呈现为紧凑执行记录；工具结果允许有边框，但不再嵌套卡片。
- 代码块顶部固定显示语言与复制按钮；亮/暗主题使用匹配的高亮方案。

#### 回复状态与 Token

- 每轮模型回复使用一个 `ReplyFooter`，紧邻最终回复底部；不再把 token 放在模型名称或消息标题行。
- 桌面布局中，本轮操作在左侧，状态指标在右下角；窄窗时状态组换到下一行并保持右对齐。
- P0 直接使用现有 `Message.token_count`，显示为 `160 tokens`。该字段目前是本轮 provider 上报的 input + output 合计，不得标成“输出 tokens”。
- token 值为 0 或未知时不渲染占位；流式完成并收到 usage 后再出现，避免跳动可预留固定最小宽度。
- 指标使用 22–24px 高的中性状态项、11px tabular numbers 和低对比背景，不能比正文或发送按钮更醒目。
- 参考 Image #1 的完整状态组顺序为：`tokens/s`、`tokens`、`duration`、`stop reason`。没有真实数据的指标不显示。
- `tokens/s` 由 `output_tokens / generation_duration` 计算；duration 从发起 provider 请求到最后一个内容事件，不包含用户在工具结果界面停留的时间。
- 正常结束原因可简写为 `EOS` 或 `Stop`，异常停止使用 warning/danger 语义色；完整原始原因放在 tooltip，不把长字符串撑宽布局。
- 当前持久化层只有合计 `token_count`。要在刷新后保留完整状态组，需要扩展消息契约：`input_tokens`、`output_tokens`、`duration_ms`、`finish_reason`。
- Gateway 已能收到 usage，Provider delta 也包含 `finish_reason`，但当前流处理没有把结束原因写入 `done` 或 Engine；实施完整状态组时必须同步 Gateway、Engine、Frontend 和数据库迁移。

#### 本轮操作

- 操作区位于同一个 `ReplyFooter` 左侧，与回复状态共享底部基线。
- P0 提供“复制最终回复”；复制成功用图标状态和 toast 反馈。
- “重新生成”只有在服务端 turn 语义明确后启用，必须生成新的 assistant turn 并保持历史一致性。
- 引用可以直接复用现有 `setDraft()`，作为后续紧邻操作；分支、分享、导出未实现前不显示。
- 操作按钮使用 28–32px 固定点击区、Lucide 图标和 tooltip；键盘 focus 时始终可见，不能只依赖 hover。

#### 滚动规则

- 对话区是主区唯一持续滚动的区域，顶部上下文栏与底部输入区不参与滚动。
- 用户距离底部不超过约 96px 时才自动跟随流式输出。
- 用户向上阅读后暂停跟随，在输入区上方显示固定尺寸的“回到最新”图标按钮。
- 不对每个 token 调用平滑 `scrollIntoView`；使用 requestAnimationFrame 节流。
- 每个对话记录独立滚动位置，切换回来时恢复。

### 3.5 底部一体式输入区

目标：与参考图一致，把 textarea、工具和发送状态放入一个大尺寸、稳定的输入工作台。

```text
┌──────────────────────────────────────────────────────────────┐
│ 输入消息                                                     │
│                                                              │
│ [命令] [联网搜索]                           [字符状态] [发送] │
└──────────────────────────────────────────────────────────────┘
```

- 输入区位于主工作区底部，外边距 12px，不悬浮覆盖消息。
- 使用单个 8–10px 圆角容器，浅色主题为中性浅灰底，暗色主题为略亮于主画布的 surface。
- textarea 无独立边框，默认两行高度，最大展开至 220px，之后内部滚动。
- placeholder 只写“输入消息”，快捷键与功能说明放到 tooltip，不在界面堆叠教学文字。
- 左侧只展示真实能力：Slash 命令、联网搜索。附件、图片、MCP 工具等能力接通后再增加按钮。
- 搜索按钮负责开关，Provider 选择放入其弹出菜单，不拆成两个紧邻小按钮。
- 右侧字符状态默认隐藏，达到 85% 后显示进度环与剩余量；警戒时使用 `warning`。
- 发送/停止固定 32×32px，图标变化不改变布局。
- 流式中允许继续在其他对话输入草稿，但当前对话的发送按钮进入 Stop 状态。
- Slash 菜单向上展开，限制在输入区宽度内，补齐 `listbox/option`、活动项关联和分组。

### 3.6 供应商与模型配置页

目标：保留现有 Settings 导航、供应商列表和供应商详情三栏骨架，只参考 Image #2 重排右侧详情内容，使 API Key、API 地址和模型管理形成从上到下的自然流程。

```text
┌ Settings ──────┬ Providers ─────────┬ DeepSeek · BUILTIN ───────────┐
│ Providers      │ [+ Add]            │ OpenAI-compatible  [启用][删除]│
│ Skills         │ Anthropic          │                                │
```

#### 页面结构

- Settings 的一级导航及其 `Providers / Skills / Knowledge / Memories / Security / Appearance / Developer` 列表保持不变。
- `ProvidersPanel` 中间列继续显示供应商列表、builtin/draft/off 状态和 Add 按钮；保留现有选中、创建、删除和滚动逻辑。
- 右侧 `ProviderDetail` 继续显示当前供应商，不改为新的全屏页面或顶部下拉选择器。
- 右侧详情头保留供应商名称、protocol、id 和 builtin/custom 信息；增加官方文档外链，把 `enabled` 从表单底部移动到标题行右侧。
- builtin 供应商的删除按钮继续禁用；custom 供应商保留删除按钮和确认框。启用与删除必须有足够间距，避免误触。
- 右侧详情正文按 API Key → API Endpoint → Models 的顺序纵向排列，使用现有详情栏宽度并独立滚动。
- 表单编辑使用本地 draft；由于现有 Gateway 通过 PUT 替换完整 profile 列表，页面底部保留明确的“放弃更改 / 保存”操作，不对每次按键自动提交。
- 现有固定底部 `Save changes` 位置和主按钮层级保留；仅在 draft 变脏且校验通过时启用。

#### API 密钥区

- 标题、输入框、显示/隐藏按钮和“检测”按钮组成一个连续控件组，按钮高度与输入框一致。
- 沿用现有 secrets vault：未设置、会话中可用、已加密保存、已锁定四种状态必须明确区分。
- vault 锁定时只显示固定掩码与锁图标；用户解锁前不能把未知 key 长度泄露到界面。
- “获取密钥”使用官方供应商链接并通过 Tauri shell 打开系统浏览器。
- “检测”只验证当前输入或已解锁的 key，不隐式保存；成功/失败通过全局 toast 和输入尾部状态图标反馈。
- 当前 Adapter 已有 `ValidateKey`，但 Gateway 没有对应路由。新增 `POST /api/v1/providers/{provider}/validate-key`，请求中的 key 继续使用 secret header，不写入日志或响应。
- 当前数据层只支持每个供应商一个 opaque key。参考图中的“多个密钥使用逗号分隔”在轮询、失败切换和安全存储契约明确前不显示。

#### API 地址区

- 输入框编辑 `ProviderProfile.base_url`；builtin 供应商可显示 SDK 默认地址的 placeholder，但不能为了展示而把空值错误持久化。
- 标题右侧提供“恢复默认”和帮助 tooltip；仅 custom provider 强制要求非空 URL。
- 输入框下方实时显示 protocol-aware 请求地址预览，例如 `/v1/chat/completions`。预览必须由统一 URL helper 生成，不能直接字符串拼接。
- URL 规范化处理尾部 `/`、已有 `/v1`、本地地址和自定义路径；保存前做结构校验，错误通过 toast 呈现并聚焦字段。
- API Key 与 URL 都属于敏感配置界面，诊断日志只能记录 provider id、协议和错误类别，不能记录 key、query 或完整响应体。

#### 模型区

- 标题行显示模型数量 badge、本地搜索、“获取模型列表”和 Plus 图标按钮。
- 少于 8 个模型时可以隐藏搜索；出现后保持固定位置，过滤仅影响当前列表显示。
- “添加”在列表顶部插入可编辑模型行，Enter 确认、Escape 取消；模型 ID 去重并保留大小写。
- 模型列表使用一个有边框的分组容器，供应商名称作为组标题；每个模型是固定高度行，不为每个模型再包独立卡片。
- 模型行至少包含供应商图标、模型 ID、设置按钮和移除按钮。builtin profile 可以编辑模型列表，但不能删除供应商本身。
- 参考图中的推理、工具、视觉等能力图标只有在服务端返回或用户明确配置 capability 时显示；不得根据模型名称猜测。
- 当前 `ProviderProfile.models` 是 `string[]`，因此 P0 先完成名称、添加、移除和同步差异预览。若要保存上下文窗口与能力，应将其演进为独立 `ModelProfile`，不能把展示元数据塞进模型 ID。
- 同步结果先展示“新增 / 保留 / 将移除”差异，由用户确认后写回 profile；远端临时失败不能清空本地模型列表。

#### 模型发现契约

- 现有 `GET /api/v1/providers/{provider}/models` 对 OpenAI-compatible Adapter 只返回 profile 中已配置的模型，不等于参考图中的远程“获取模型列表”。
- 新增独立的 `POST /api/v1/providers/{provider}/models/discover`，使用当前草稿 API URL 与临时 key 请求远端，不直接持久化。
- 返回结构至少包含 `id`、`name`、`provider` 和可选 `context_limit/capabilities`；无法列出模型的供应商返回明确的 `discovery_supported: false`，UI 保留手工添加。
- “检测密钥”和“发现模型”是两个命令：检测只回答凭据/连接是否有效，发现模型返回候选列表，二者不能复用含糊成功状态。
- capability schema 未稳定前保留未知字段但不渲染空图标；后续模型设置页再处理默认采样参数、推理模式与工具支持。

#### 状态与响应式

- 加载时用与标题、三个字段区和模型行等高的骨架，不显示整页 spinner。
- 检测、发现和保存具有独立 pending 状态；其中一个请求进行时不应锁死其他只读区域。
- 窄窗下控件组允许换行：“检测”“获取模型列表”和添加按钮保持至少 32px 点击区，输入框优先占满整行。
- 所有 secret、URL 和模型输入都有显式 label；显示/隐藏、重置、帮助、搜索、添加、设置和移除均有 `aria-label` 与 tooltip。

### 4.1 色彩层级

不照抄参考图的绿色品牌色，保留 EncoreHub accent，但严格复用参考图的明度关系。

- 桌面正文 14px，消息正文 15–16px，元数据 11–12px，主区顶部名称 14px。

- 动效仅用于标签切换、菜单出现、侧栏折叠和状态变化，时长 120–180ms，并支持 reduced motion。

## 九、风险与非目标

### 主要风险

- **角色数据缺口**：当前代码没有 CharacterProfile。布局可以先落地默认角色，但添加角色和全局提示词不能只做前端假数据。
- **角色卡兼容面**：不同 Tavern/SillyTavern 版本和扩展字段存在差异，必须用版本化适配器与真实夹具验证，不能只支持单个示例 JSON。
- **模型显示错配**：现有全局 ProviderSwitcher 与 Conversation 权威模型语义不同，迁移顶部栏时必须一并修正。
- **模型发现语义**：现有 ListModels 仅返回已配置模型。若不增加独立 discover 契约，按钮会产生“已同步但没有访问远端”的误导。
- **回复遥测迁移**：完整状态组涉及数据库、Engine、Gateway SSE 和 Frontend 类型；字段必须可选并兼容既有消息。
- **自定义标题栏**：窗口拖拽和跨平台行为风险高，必须晚于普通布局并保留平台降级。
- **宽幅消息可读性**：目标是 960–1080px 容器，不代表纯文本行撑满；Markdown 段落可用更窄的字符行宽，表格/代码再利用全宽。
- **低高度窗口**：大输入区可能挤压消息区，需要专门的紧凑高度模式。

### 本轮不做

- 不做活动栏或 Knowledge/Memory/Skills 一级工作区。
- 不做用户与模型回复对称的左右双气泡；仅用户消息使用右侧气泡，模型回复保持文档流。
- 不添加尚未接通的附件、多模型并行、导出、分支和搜索按钮。
- 不为了截图一次性关闭所有平台原生窗口装饰。
- 不引入营销式首页、Hero、大面积渐变或装饰性卡片。
- 不支持尚无负载均衡策略的逗号分隔多 Key。
- 不在 UI 改版阶段声称完整支持所有酒馆角色卡版本；先固定兼容契约和无损字段保留。
- 不重写无关 services 和 Zustand 数据流；角色、模型发现和回复遥测只做必要的契约扩展。
